# Question 2 — a small DOS shell emulator

Source: [Q2.ASM](../Q2.ASM).

This is a larger program than the password checker because it combines three
jobs: reading a command line, deciding what that line means, and performing a
DOS operation. We will keep those jobs separate while following the actual
source.

The accepted commands are:

```text
DIR
TYPE <filename>
COPY <source> <destination>
EXIT
```

The assignment comment mentions a mock directory listing. **This implementation
uses real DOS directory and file services**, including creation or truncation
of a real destination for `COPY`. It does not merely print hardcoded mock names.

As in Assignment 1, each section explains a small piece, then connects it to
8085 ideas where useful.

---

## 1. What a shell does in this program

A shell repeatedly performs:

```text
prompt → read → parse → dispatch → perform operation → prompt again
```

Here “parse” means identify the command, count its arguments, and extract the
filename tokens.

“Dispatch” means choose the corresponding procedure. It is implemented with
comparisons and jumps, rather than a special shell instruction.

There is no facility to launch arbitrary executables. A command such as
`FORMAT`, `CD`, or `MYPROG` is rejected, regardless of what DOS could run outside
this emulator.

---

## 2. Overall control flow

```text
MAIN
  ├─ initialize DS/ES
  ├─ print title/help line
  └─ SHELL_LOOP
       ├─ print SHELL> prompt
       ├─ READ_COMMAND
       ├─ PARSE_COMMAND → AL = command identifier
       │
       ├─ DIR  → DO_DIR  ─┐
       ├─ TYPE → DO_TYPE ─┼─> SHELL_LOOP
       ├─ COPY → DO_COPY ─┘
       ├─ EXIT → print goodbye → terminate
       ├─ blank line → SHELL_LOOP
       └─ invalid line → print error → SHELL_LOOP
```

`MAIN` initializes the segments, prints the title, and runs this dispatch loop.
The file-operation procedures return after success or failure. A missing
source file does not terminate the shell.

---

## 3. Stack, data, and code

```asm
STACKSEG SEGMENT PARA STACK 'STACK'
    DW 128 DUP (?)
STACKSEG ENDS
```

The stack has 256 bytes. Near calls push return offsets; helpers also save
working registers using word-sized `PUSH` instructions.

The data segment holds messages, input, parsed tokens, file handles, transfer
storage, and DOS directory-search storage.

The code segment holds the shell loop and all its procedures.

```asm
ASSUME CS:CODESEG, DS:DATASEG, SS:STACKSEG
```

describes segment use to MASM. At run time:

```asm
MOV AX, DATASEG
MOV DS, AX
MOV ES, AX
```

actually initializes registers. These routines use ordinary `DS` memory
addressing rather than string instructions requiring `ES`; setting `ES` here
does not itself copy anything.

---

## 4. Command identifiers

```asm
CMD_NONE EQU 0
CMD_DIR  EQU 1
CMD_TYPE EQU 2
CMD_COPY EQU 3
CMD_EXIT EQU 4
```

These constants let the parser return a small number rather than requiring
the main loop to compare command strings again.

```text
text "COPY" → parser → identifier 3 → dispatcher → DO_COPY
```

`EQU` allocates no storage. In contrast:

```asm
COMMAND_ID  DB CMD_NONE
PARSE_ERROR DB 0
```

creates two memory bytes that change while a line is parsed.

---

## 5. Parser status has two parts

| Variable | Meaning |
| --- | --- |
| `COMMAND_ID` | Valid operation, or `CMD_NONE` |
| `PARSE_ERROR=0` | No parser error; may be a blank line |
| `PARSE_ERROR=1` | Unknown command or invalid argument structure |
| `PARSE_ERROR=2` | COPY source and destination have the same spelling ignoring case |

This lets a blank line do nothing while a malformed line gets a message.

The parser resets both bytes on every call. Otherwise an old valid command
could accidentally survive into a new input line.

---

## 6. Three ways of representing text

The source deliberately uses different formats for different DOS services.

| Kind of data | Representation | Consumer |
| --- | --- | --- |
| Fixed messages | `$` terminated | DOS `09H` |
| Command spellings, filenames, wildcard | Zero terminated, ASCIIZ | Parser and DOS filename services |
| File contents | Explicit byte count | DOS `3FH` and `40H` |

For example:

```asm
PROMPT_MSG   DB 13,10,'SHELL> $'
CMD_DIR_TEXT DB 'DIR',0
ALL_FILES    DB '*.*',0
IO_BUFFER    DB 128 DUP (0)
```

A literal `$` inside a file is ordinary file data. It does not terminate the
count-based output performed by `TYPE`.

---

## 7. The DOS input buffer layout

```asm
COMMAND_BUFFER DB 126,0,127 DUP (0)
```

For DOS buffered keyboard service `0AH`, the beginning is:

```text
offset +0 → buffer capacity, including carriage-return capacity
offset +1 → returned character count, excluding the carriage return
offset +2 → first typed character
```

For the line `DIR`:

```text
+0   +1   +2   +3   +4   +5
126   3   'D'  'I'  'R'  CR
```

The character area is generously allocated. The parser later sees an ASCIIZ
line because `READ_COMMAND` replaces the returned CR with zero.

---

## 8. Token capacities

```asm
COMMAND_TOKEN DB 16 DUP (0)
SOURCE_NAME   DB 64 DUP (0)
DEST_NAME     DB 64 DUP (0)
```

One byte in each array is reserved for the final zero.

```text
command storage → up to 15 characters plus zero
source storage  → up to 63 characters plus zero
dest storage    → up to 63 characters plus zero
```

These are parser buffer capacities, not a promise that DOS accepts every
63-character filename spelling. Filename and path rules still belong to the
DOS environment.

---

## 9. File handles are not memory addresses

```asm
SOURCE_HANDLE DW 0
DEST_HANDLE   DW 0
READ_COUNT    DW 0
```

Opening a file returns a small handle number in `AX`. Later operations put
that number in `BX` to select the file.

The handle identifies an operating-system resource. It is not the address of
the file's contents in RAM.

`READ_COUNT` saves how many bytes a successful read actually returned. The
copy operation must write that count, rather than always writing all 128 bytes
of the transfer buffer.

---

## 10. Begin the shell loop

```asm
LEA DX, PROMPT_MSG
CALL PRINT_STRING
CALL READ_COMMAND
CALL PARSE_COMMAND
```

`DX` supplies an offset; with `DS`, it identifies the message.

The two calls have different results:

```text
READ_COMMAND  → modifies COMMAND_BUFFER in memory
PARSE_COMMAND → modifies token/status memory and returns command ID in AL
```

Knowing a procedure's result location is more useful than assuming every
procedure returns its answer in `AX`.

---

## 11. Dispatch using comparisons

```asm
CMP AL, CMD_DIR
JE RUN_DIR
CMP AL, CMD_TYPE
JE RUN_TYPE
CMP AL, CMD_COPY
JE RUN_COPY
CMP AL, CMD_EXIT
JE RUN_EXIT
```

`CMP` sets flags without changing `AL`. `JE` branches on equality.

This is the assembly equivalent of a chain of `if` statements or a `switch`.
In 8085 you would recognize the same idea as repeated `CPI` and `JZ` tests on
the accumulator.

Each handler calls its operation and jumps back to `SHELL_LOOP`; `RUN_EXIT`
instead prints the goodbye message and invokes DOS `4C00H` termination.

---

## 12. Blank input and invalid input

If none of the four identifiers matched, the dispatcher checks `PARSE_ERROR`.

```asm
CMP PARSE_ERROR, 0
JE SHELL_LOOP
CMP PARSE_ERROR, 2
JE SHOW_SAME_FILE
```

Zero means no error message is needed. Error 2 chooses the specific same-file
message; any remaining parser error uses the general syntax message.

The shell accepts blank lines and space-only lines without treating them as
unknown commands.

---

## 13. `READ_COMMAND`: call DOS line input

```asm
MOV COMMAND_BUFFER[1], 0
LEA DX, COMMAND_BUFFER
MOV AH, 0AH
INT 21H
```

The previous returned count is cleared before the new read. DOS echoes the
typed line and performs its line-input handling.

The routine preserves `AX`, `BX`, `DX`, and `SI` around its work. Its output is
the stored line, so none of these registers needs to be a return-value register.

This differs from Question 1's per-key BIOS input: the shell delegates line
collection to DOS instead of handling Backspace and printable keys itself.

---

## 14. Replace the CR with zero

```asm
XOR BX, BX
MOV BL, COMMAND_BUFFER[1]
LEA SI, COMMAND_BUFFER[2]
ADD SI, BX
MOV BYTE PTR [SI], 0
```

If the line contained three characters, `SI` advances three bytes from the
start of the character area to the CR after them.

```text
before: D I R CR
after:  D I R 00H
```

`BYTE PTR` tells MASM that the zero store is one byte wide. Without an explicit
type, a bare pointer plus immediate value can leave the intended width unclear.

Clearing `BX` first ensures that the byte count is zero-extended into a valid
word offset.

---

## 15. `PARSE_COMMAND`: extract and normalize the command

```asm
MOV COMMAND_ID, CMD_NONE
MOV PARSE_ERROR, 0
LEA SI, COMMAND_BUFFER[2]
LEA DI, COMMAND_TOKEN
MOV CX, 15
CALL GET_TOKEN
CMP AL, 0
JE PARSE_FINISHED
```

The initial `GET_TOKEN` returns 0 if no word exists. The reset state then means
“blank input,” not a syntax failure.

If a word exists:

```asm
LEA SI, COMMAND_TOKEN
CALL UPPERCASE_STRING
```

normalizes only the command token.

```text
"dir"  → "DIR"
"TyPe" → "TYPE"
```

The original line and filename spellings remain separate.

---

## 16. Compare the complete command token

The parser repeatedly loads the command token and an expected string:

```asm
LEA SI, COMMAND_TOKEN
LEA DI, CMD_DIR_TEXT
CALL STR_EQUAL
CMP AL, 1
JE PARSE_DIR
```

It does the same for `TYPE`, `COPY`, and `EXIT`.

`STR_EQUAL` requires both strings to end together. Thus `DIRECTORY` does not
match `DIR` merely because its first three letters agree.

If no expected spelling matches, execution reaches `PARSE_INVALID`.

---

## 17. Why restart from the original line?

Command recognition reused `SI` for the command-token string. To find arguments,
each command-specific parser starts again at:

```asm
LEA SI, COMMAND_BUFFER[2]
CALL MOVE_PAST_COMMAND
```

`MOVE_PAST_COMMAND` skips leading literal spaces, then advances through the
command word until a space or zero.

For:

```text
   TYPE   NOTES.TXT
```

it leaves `SI` at the first space after `TYPE`. The next `GET_TOKEN` skips those
spaces and reads `NOTES.TXT`.

---

## 18. `DIR` and `EXIT` take no arguments

After moving past the command, both branches call `HAS_MORE_TEXT`.

```asm
CALL HAS_MORE_TEXT
CMP AL, 1
JE PARSE_INVALID
```

Trailing spaces are allowed; any nonspace character is rejected.

```text
DIR        → valid
DIR        → valid even with trailing spaces
DIR *.TXT  → invalid in this implementation
EXIT NOW   → invalid
```

The shell's `DIR` always searches `*.*`; a user-supplied wildcard argument is
not part of the supported syntax.

---

## 19. `TYPE` requires exactly one token

```asm
LEA DI, SOURCE_NAME
MOV CX, 63
CALL GET_TOKEN
CMP AL, 0
JE PARSE_INVALID
CALL HAS_MORE_TEXT
CMP AL, 1
JE PARSE_INVALID
```

This accepts one filename token, rejects a missing filename, and rejects an
extra argument.

```text
TYPE NOTES.TXT        → syntactically valid
TYPE                 → invalid
TYPE NOTES.TXT EXTRA  → invalid
```

Syntactically valid does not mean the file exists. Existence and access errors
are handled later by `DO_TYPE`.

---

## 20. `COPY` requires two tokens

The source and destination calls are:

```asm
LEA DI, SOURCE_NAME
MOV CX, 63
CALL GET_TOKEN
```

and:

```asm
LEA DI, DEST_NAME
MOV CX, 63
CALL GET_TOKEN
```

`GET_TOKEN` advances `SI` over each full input token, so the second call finds
the next argument.

After both succeed, `HAS_MORE_TEXT` rejects a third argument. Then `SAME_NAMES`
checks the two saved spellings.

Only after all checks succeed does the parser set `COMMAND_ID` to `CMD_COPY`.

---

## 21. Same-name checking is textual

```asm
LEA SI, SOURCE_NAME
LEA DI, DEST_NAME
CALL SAME_NAMES
CMP AL, 1
JE PARSE_SAME_FILE
```

`A.TXT` and `a.txt` compare equal after ASCII case folding. The parser rejects
the operation before a destination can be created.

However:

```text
A.TXT
.\A.TXT
```

have different text even if DOS resolves them to the same file.

The routine does not canonicalize paths or compare filesystem identities.
Consequently its check is incomplete protection against copying a file onto
itself: a differently spelled alias may reach create/truncate and destroy the
source contents.

---

## 22. Finish parsing with a deliberate return value

`PARSE_INVALID` writes 1 to `PARSE_ERROR`. `PARSE_SAME_FILE` writes 2.

Neither sets a valid command ID, so the initial `CMD_NONE` survives.

At `PARSE_FINISHED`, saved scratch registers are restored and:

```asm
MOV AL, COMMAND_ID
RET
```

returns the identifier. Restoring `AX` here would overwrite `AL`, which is why
this procedure does not preserve `AX` as a whole.

---

## 23. `GET_TOKEN`: skip spaces and detect absence

The helper receives:

```text
DS:SI → input position
DS:DI → output token buffer
CX    → maximum stored characters, excluding final zero
```

It first skips literal space bytes. If the next byte is zero, there is no token:

```asm
MOV BYTE PTR [DI], 0
MOV AL, 0
```

Otherwise it clears `BX`, its stored-character count, and begins scanning.

Unlike a standard whitespace tokenizer, this routine does not treat Tab as a
separator. It also has no quote or escape processing.

---

## 24. `GET_TOKEN`: store a bounded prefix

```asm
CMP BX, CX
JAE GET_CONSUME
MOV [DI+BX], AL
INC BX
```

When the capacity is exhausted, the store is skipped, but scanning continues:

```asm
GET_CONSUME:
    INC SI
    JMP GET_COPY
```

This preserves the boundary of the next argument. It does not split one long
argument into several tokens.

At a space or zero:

```asm
MOV BYTE PTR [DI+BX], 0
MOV AL, 1
```

returns a terminated token and “a token existed.” It does **not** return
“every input character fit.”

---

## 25. A small token trace

Imagine calling `GET_TOKEN` with storage limit 3 on the input:

```text
  ABCDE NEXT
```

| Input action | Stored token | BX |
| --- | --- | --- |
| Skip two spaces | empty | not yet used |
| Accept A | A | 1 |
| Accept B | AB | 2 |
| Accept C | ABC | 3 |
| Consume D without storing | ABC | 3 |
| Consume E without storing | ABC | 3 |
| Stop at space | ABC followed by zero | 3 |

`SI` now points to the space before `NEXT`. Another call skips it and reads the
next token.

The real limits are 15 and 63, but this smaller example shows the same branch.

---

## 26. `HAS_MORE_TEXT` is a syntax helper

It skips literal spaces starting at `SI`, then returns:

```text
AL = 0 → reached zero; no extra argument text
AL = 1 → encountered nonspace text
```

It does not copy or validate another token. It merely answers whether any
unconsumed text remains.

Because it advances `SI`, the next operation could continue at that text if
needed. In this source the callers use its Boolean result to accept or reject
the completed argument list.

---

## 27. `UPPERCASE_STRING` changes only lowercase ASCII

```asm
CMP AL, 'a'
JB UPPER_NEXT
CMP AL, 'z'
JA UPPER_NEXT
SUB BYTE PTR [SI], 20H
```

ASCII lowercase and uppercase letters differ by 32 (`20H`). The range checks
ensure that digits and punctuation are not modified.

```text
'd' = 64H
'D' = 44H
64H − 20H = 44H
```

The routine scans to zero, then restores `AX` and the original `SI`. Its result
is an in-place memory change, not a returned uppercase character in `AL`.

---

## 28. `STR_EQUAL`: compare two ASCIIZ strings

```asm
MOV AL, [SI]
MOV BL, [DI]
CMP AL, BL
JNE STR_NOT_EQUAL
CMP AL, 0
JE STR_IS_EQUAL
INC SI
INC DI
JMP STR_EQUAL_LOOP
```

A mismatch returns 0 immediately. Equal zero bytes mean both strings have
ended at the same position, so it returns 1.

The routine preserves `BX`, `SI`, and `DI`, but not its result register `AL`.

8085 connection: you could implement the same byte loop using `HL` and another
register pair, loading one comparison byte into `A`. The algorithm is familiar;
8086's independently addressable index registers make the expression simpler.

---

## 29. `SAME_NAMES`: compare without rewriting filenames

`SAME_NAMES` loads the current characters into `AL` and `DL`, conditionally
subtracts `20H` from lowercase letters in those registers, then compares them.

Unlike `UPPERCASE_STRING`, it does not change filename bytes in memory.

```text
stored source: "notes.txt"
stored dest:   "NOTES.TXT"
temporary compared bytes: uppercase on both sides
result: equal
```

Equal zero terminators finish a successful comparison. A mismatch returns 0.
The procedure preserves `BX`, `DX`, `SI`, and `DI` and returns its Boolean in
`AL`.

---

## 30. DOS services used by the file operations

| AH / AX | Operation | Important inputs | Success result |
| --- | --- | --- | --- |
| `1AH` | Set DTA | `DS:DX` buffer | Subsequent searches use that DTA |
| `4EH` | Find first | `DS:DX` wildcard, `CX` attributes | DTA filled; CF clear |
| `4FH` | Find next | Existing DTA search state | DTA filled; CF clear |
| `3D00H` | Open read-only | `DS:DX` ASCIIZ path | `AX` handle; CF clear |
| `3CH` | Create/truncate | `DS:DX` path, `CX` attributes | `AX` handle; CF clear |
| `3FH` | Read | `BX` handle, `CX` count, `DS:DX` buffer | `AX` bytes read |
| `40H` | Write | Same handle/count/buffer convention | `AX` bytes written |
| `3EH` | Close | `BX` handle | CF clear on success |

For the file services that report errors through carry, CF set means the
operation failed and `AX` contains an error code. This program prints general
messages rather than decoding that error code.

---

## 31. `DO_DIR`: provide a private DTA

```asm
LEA DX, DTA_BUFFER
MOV AH, 1AH
INT 21H
```

The Disk Transfer Area holds both directory-search state and a returned entry.
It is not the same thing as the file transfer buffer `IO_BUFFER`.

The source reserves 128 bytes for it and leaves it installed for later searches
within this process. It does not save and restore the previous DTA pointer.

In a more general helper library, restoring global process state could matter
to callers. This shell has no external command-launching path that would rely
on a restored DTA inside the emulator.

---

## 32. Find the first match

```asm
LEA DX, ALL_FILES
XOR CX, CX
MOV AH, 4EH
INT 21H
JC DIR_EMPTY
```

`ALL_FILES` contains the zero-terminated wildcard `*.*`.

`CX=0` selects the ordinary-file search behavior, rather than requesting
directory, hidden, or system entries through the attribute mask.

A successful search fills the DTA. On failure, the program prints “No files
found.” It does not distinguish an empty match set from other FindFirst errors.

---

## 33. Print the DTA filename and continue

```asm
LEA DX, DTA_BUFFER[30]
CALL PRINT_ZSTRING
LEA DX, NEWLINE
CALL PRINT_STRING
MOV AH, 4FH
INT 21H
JNC DIR_PRINT_NEXT
```

The classic DOS search-result filename begins at DTA offset 30 (`1EH`) and is
zero terminated.

Each successful FindNext replaces the current result. Carry set ends the loop,
whether it indicates search exhaustion or another error.

There is no sorting phase, file-size display, or recursive traversal. The
program prints names in the order returned by the DOS search.

---

## 34. `DO_TYPE`: open the selected source

```asm
LEA DX, SOURCE_NAME
MOV AX, 3D00H
INT 21H
JC TYPE_OPEN_ERROR
MOV SOURCE_HANDLE, AX
```

`AH=3DH` selects open and `AL=00H` selects read-only access.

Only a successful open gives a valid handle to save. On open failure, the
program prints its source-open error without closing an unacquired handle.

This is why cleanup paths must depend on which operations actually succeeded.

---

## 35. Read one chunk

```asm
MOV BX, SOURCE_HANDLE
LEA DX, IO_BUFFER
MOV CX, 128
MOV AH, 3FH
INT 21H
JC TYPE_READ_ERROR
CMP AX, 0
JE TYPE_COMPLETE
```

The request is “up to 128 bytes,” not “exactly 128 bytes.”

```text
CF=1       → read failed
CF=0, AX=0 → end of file
CF=0, AX>0 → that many valid bytes are now in IO_BUFFER
```

Bytes beyond `AX` in the buffer may contain old data and must not be printed.

---

## 36. Write the returned bytes to standard output

```asm
MOV CX, AX
MOV BX, 1
LEA DX, IO_BUFFER
MOV AH, 40H
INT 21H
JC TYPE_WRITE_ERROR
CMP AX, CX
JNE TYPE_WRITE_ERROR
```

Handle 1 is standard output. On an ordinary console run it is the display, but
the code uses the DOS handle interface rather than a direct video-memory write.

It checks both carry and the returned count. A short successful write is still
insufficient to display the whole requested chunk.

After a full write it returns to the read loop.

---

## 37. `TYPE` cleanup paths

| Path | What is closed? | What is printed? |
| --- | --- | --- |
| Open failed | Nothing | Source-open error |
| Read failed | Source | Read error |
| Output failed or short | Source | Write error |
| EOF reached | Source | A final newline |

Close return codes are not checked.

The routine restores `AX`, `BX`, `CX`, and `DX`, then returns to the shell.

`TYPE` copies raw bytes to output; it does not decode text, filter control
characters, or treat byte `1AH` as an instruction to stop reading. The read
count and end-of-file result govern its loop.

---

## 38. `DO_COPY`: open before creating

The source is opened read-only first, using the same `3D00H` sequence as TYPE.

Only after that succeeds does the program create the destination:

```asm
LEA DX, DEST_NAME
XOR CX, CX
MOV AH, 3CH
INT 21H
JC COPY_CREATE_ERROR
MOV DEST_HANDLE, AX
```

`CX=0` requests normal file attributes. Service `3CH` creates a new file or
truncates an existing destination.

This is a real overwrite operation with no interactive overwrite prompt.

---

## 39. Copy exactly the bytes read

```asm
CMP AX, 0
JE COPY_COMPLETE
MOV READ_COUNT, AX
```

After a successful nonempty read, the actual count is saved before preparing
the write:

```asm
MOV BX, DEST_HANDLE
MOV CX, READ_COUNT
LEA DX, IO_BUFFER
MOV AH, 40H
INT 21H
JC COPY_WRITE_ERROR
CMP AX, READ_COUNT
JNE COPY_WRITE_ERROR
```

Saving the count in memory makes the intended invariant explicit:

```text
bytes requested for output = bytes actually obtained from input
```

---

## 40. Worked transfer: a 300-byte file

With a 128-byte buffer:

| Read call | Requested | Returned AX | Written to destination |
| --- | --- | --- | --- |
| 1 | 128 | 128 | 128 |
| 2 | 128 | 128 | 128 |
| 3 | 128 | 44 | 44 |
| 4 | 128 | 0 | Nothing; EOF |

Total:

```text
128 + 128 + 44 = 300 bytes
```

Writing 128 bytes after the third read would append 84 stale bytes. The
`READ_COUNT` logic prevents that.

The memory requirement stays 128 transfer bytes even for a much larger file,
because the program streams chunks rather than loading the whole file.

---

## 41. COPY error paths follow handle ownership

| Failure point | Acquired handles | Cleanup |
| --- | --- | --- |
| Source open | None | Print open error |
| Destination create | Source only | Close source; print create error |
| Read after both opens | Source and destination | Close both; print read error |
| Write or short write | Source and destination | Close both; print write error |
| EOF after complete writes | Source and destination | Close both; print success |

`COPY_CREATE_ERROR` must not call the two-handle closer because no destination
handle was acquired on that path.

The global handle words may contain old values, so “a word exists in memory”
does not establish ownership. The executed success path establishes ownership.

---

## 42. `CLOSE_COPY_HANDLES`

```asm
MOV BX, DEST_HANDLE
MOV AH, 3EH
INT 21H
MOV BX, SOURCE_HANDLE
MOV AH, 3EH
INT 21H
```

The helper closes the destination first, then the source, preserving its
caller's `AX` and `BX`.

It does not inspect close errors. Therefore the success message means the
read/write loop reached EOF with full writes; it is not evidence that every
possible close-time failure was detected.

A failed copy also leaves any created or partially written destination in
place. There is no rollback, deletion, or retry of a short write.

---

## 43. `PRINT_STRING` for fixed messages

```asm
PUSH AX
MOV AH, 09H
INT 21H
POP AX
RET
```

It receives `DS:DX` and prints until `$`, preserving `AX`.

This helper is suitable for the fixed messages declared with dollar
terminators. Passing an arbitrary zero-terminated filename would use the wrong
format: DOS `09H` does not stop at zero.

---

## 44. `PRINT_ZSTRING` for directory names

The helper copies the starting offset into `SI` and counts bytes until zero:

```asm
MOV SI, DX
XOR CX, CX

PZS_COUNT:
    CMP BYTE PTR [SI], 0
    JE PZS_WRITE
    INC SI
    INC CX
    JMP PZS_COUNT
```

`DX` remains at the beginning while `SI` scans forward. This distinction is
essential: output still needs the original starting address.

Then:

```asm
MOV BX, 1
MOV AH, 40H
INT 21H
```

writes exactly `CX` bytes. The zero terminator itself is not included.

Unlike TYPE and COPY, this small display helper does not check carry or a
short write. It restores `AX`, `BX`, `CX`, `DX`, and `SI` afterward.

---

## 45. Worked parser example

Input:

```text
  copy   alpha.txt   beta.txt
```

The stages are:

```text
GET_TOKEN           → COMMAND_TOKEN = "copy"
UPPERCASE_STRING    → COMMAND_TOKEN = "COPY"
STR_EQUAL           → matches CMD_COPY_TEXT
MOVE_PAST_COMMAND   → SI at spaces after original "copy"
GET_TOKEN           → SOURCE_NAME = "alpha.txt"
GET_TOKEN           → DEST_NAME = "beta.txt"
HAS_MORE_TEXT       → AL = 0
SAME_NAMES          → AL = 0, spellings differ
COMMAND_ID          → CMD_COPY = 3
PARSE_COMMAND return→ AL = 3
MAIN dispatch       → DO_COPY
```

This trace establishes syntax acceptance. Whether the copy succeeds depends
on the real files and DOS errors when the operation runs.

## 46. Syntax examples and nonfeatures

| Line | Parser outcome |
| --- | --- |
| Empty or spaces only | Prompt again silently |
| `dir` | DIR |
| `DIR A.TXT` | Invalid: extra argument |
| `TYPE A.TXT` | TYPE |
| `TYPE` | Invalid: missing argument |
| `COPY A.TXT B.TXT` | COPY |
| `COPY A.TXT a.txt` | Same-file error |
| `COPY A.TXT B.TXT C.TXT` | Invalid: third argument |
| `EXIT` | Terminate |
| `EXIT NOW` | Invalid: extra argument |

Quoting does not combine words. `TYPE "A B.TXT"` is split at the space, so it
does not provide a filename containing a space.

There are no pipes, redirection operators parsed by this shell, wildcard-copy
expansion, command chaining, or directory-changing commands.

## 47. Whole-program pseudocode

```text
print title
repeat:
    print prompt
    line = read_DOS_line()
    replace its CR with zero
    command_id, parse_error = parse(line)

    if command_id == DIR:
        set private DTA
        find first ordinary *.* match
        if search failed:
            print no-files message
        else:
            repeat:
                print current DTA filename
                find next match
            until search fails

    else if command_id == TYPE:
        open source read-only
        if open failed:
            print open error
        else:
            repeat read chunks and write exact counts to stdout
            stop at EOF or error
            close source and report as needed

    else if command_id == COPY:
        open source read-only
        create/truncate destination if source open succeeded
        if both acquired:
            repeat read chunks and write exact counts to destination
            stop at EOF or error
            close both and report result
        else:
            close only acquired source if necessary
            print error

    else if command_id == EXIT:
        print goodbye
        terminate with status 0

    else if parse_error != 0:
        print corresponding parser error
```

## 48. The invariants worth remembering

During tokenization:

```text
0 <= stored length <= capacity
SI consumes the complete input token
output always receives a final zero
```

During successful chunk transfer:

```text
0 < valid bytes <= 128
write request count = most recent successful read count
```

During cleanup:

```text
close only handles whose open/create operations succeeded
```

These statements explain why the code branches where it does. They are more
useful than memorizing label names in isolation.

## 49. Source limitations to describe accurately

Long tokens are truncated rather than rejected. Filename truncation may cause
an operation on a shorter stored spelling than the user typed.

Same-file checking compares case-folded text, not canonical paths. Aliases can
bypass it and make COPY truncate its own source.

Existing destinations are overwritten without prompting. A transfer failure
may leave a truncated or partial destination.

FindFirst/FindNext errors are not distinguished from “no files” or search
completion. Close errors and directory-name output errors are not checked.

The emulator exposes four internal operations, not the full DOS command set.
These are properties of this source, not proposed changes made by this guide.

## 50. Connection to your 8085 knowledge

| 8085 idea | What you see here |
| --- | --- |
| Compare accumulator and conditionally jump | `CMP` followed by `JE`, `JNE`, `JB`, `JAE` |
| Advance an HL pointer | `INC SI` or `INC DI` |
| Explicit character-copy loop | `GET_TOKEN` with indexed stores |
| Save working register pairs | Word `PUSH`/`POP` around procedures |
| Call monitor I/O routines | BIOS/DOS service calls in this PC environment |
| Maintain a small control variable | `COMMAND_ID` and `PARSE_ERROR` |

8085 does not provide DOS file handles or these `INT 21H` services as CPU
features. They are supplied by the operating system running on the x86 PC.

Likewise, `SOURCE_NAME[SI]`-style address calculations are x86 addressing
features; the algorithm can be transferred to 8085, but the instruction spelling
and address preparation must change.

## 51. Exam-ready explanation

The program repeatedly reads an echoed DOS command line, replaces its trailing
carriage return with zero, extracts a space-delimited command token, and converts
that token to uppercase. It validates the number of filename arguments and
returns a command identifier to the main dispatcher.

DIR enumerates real directory entries with a private DTA and DOS FindFirst/
FindNext. TYPE opens a real source file and streams 128-byte chunks to standard
output. COPY opens the source, creates or truncates the destination, and writes
exactly the count returned by each read. File handles are closed according to
which operations succeeded. EXIT terminates the process.

The key new ideas are command parsing, multiple string formats, DOS file handles,
carry-based error reporting, count-based I/O, and cleanup along different error
paths. These build on the comparisons, pointer loops, procedures, and stack
usage you already know from 8085 and Assignment 1.
