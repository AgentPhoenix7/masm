Good—Question 2 builds directly on Question 1, but the main algorithm is actually more interesting because it introduces **comparison, conditional jumps, swapping, and using an index parity to decide the required relation**. 🔥

The goal is:

```text
a[0] < a[1] > a[2] < a[3] > a[4] ...
```

So the array should alternate like a zig-zag:

```text
small < large > small < large > small ...
```

For example, if the input is:

```text
8 3 7 2 9
```

the algorithm rearranges adjacent values so the relation becomes:

```text
3 < 8 > 2 < 9 > 7
```

The key part is not the input/output code. The key part is this block:

```asm
MOV SI, 4000H
MOV CX, 19
XOR BL, BL

ZIGZAG_LOOP:
    MOV AL, [SI]
    MOV AH, [SI+1]

    TEST BL, 1
    JNZ WANT_GREATER

    CMP AL, AH
    JB PAIR_OK
    JMP SHORT SWAP_PAIR

WANT_GREATER:
    CMP AL, AH
    JA PAIR_OK

SWAP_PAIR:
    MOV [SI], AH
    MOV [SI+1], AL

PAIR_OK:
    INC SI
    INC BL
    LOOP ZIGZAG_LOOP
```

Let’s understand that deeply.

---

# 1. First: why are there 19 comparisons?

There are 20 elements:

```text
a[0], a[1], a[2], ..., a[19]
```

Adjacent comparisons are:

```text
a[0] with a[1]
a[1] with a[2]
a[2] with a[3]
...
a[18] with a[19]
```

That gives:

```text
19 adjacent pairs
```

So:

```asm
MOV CX, 19
```

is correct.

---

# 2. `SI` points to the current pair

```asm
MOV SI, 4000H
```

Initially:

```text
SI = 4000H
```

Therefore:

```asm
MOV AL, [SI]
MOV AH, [SI+1]
```

means:

```text
AL = a[0]
AH = a[1]
```

On the next iteration:

```asm
INC SI
```

so:

```text
SI = 4001H
```

and now:

```text
AL = a[1]
AH = a[2]
```

Then:

```text
a[2], a[3]
```

and so on.

This is an important x86 addressing feature:

```asm
[SI+1]
```

means:

> access the byte one location after the address in `SI`.

In 8085, you would normally need to increment HL or use another register pair. x86 gives you this offset addressing directly.

---

# 3. Why use AL and AH?

Here:

```asm
MOV AL, [SI]
MOV AH, [SI+1]
```

the program stores two adjacent bytes in the two halves of AX.

Remember:

```text
AX
┌─────────┬─────────┐
│   AH    │   AL    │
│ 8 bits  │ 8 bits  │
└─────────┴─────────┘
```

So:

```text
AL = left value
AH = right value
```

For example:

```text
a[i]   = 20
a[i+1] = 50
```

then:

```text
AL = 20
AH = 50
```

That makes comparing and swapping easy.

---

# 4. Why `XOR BL, BL`?

```asm
XOR BL, BL
```

means:

```text
BL = 0
```

Here BL is being used as the **pair number**.

Initially:

```text
BL = 0
```

Then after every pair:

```asm
INC BL
```

So:

```text
BL = 0, 1, 2, 3, 4, ...
```

The program uses whether BL is even or odd to determine which relation is required.

---

# 5. Required relation by position

We need:

```text
a[0] < a[1]
a[1] > a[2]
a[2] < a[3]
a[3] > a[4]
...
```

So:

```text
pair index 0 → <
pair index 1 → >
pair index 2 → <
pair index 3 → >
```

Therefore:

```text
even pair number → <
odd pair number  → >
```

BL tracks exactly that.

---

# 6. `TEST BL, 1`

This is a very useful instruction:

```asm
TEST BL, 1
```

`TEST` performs a bitwise AND for the purpose of setting flags, but it does **not** store the result.

So conceptually:

```text
BL AND 1
```

The least significant bit tells whether a number is even or odd.

Examples:

```text
0 = 00000000
1 = 00000001
2 = 00000010
3 = 00000011
```

Looking at bit 0:

```text
0 → 0 → even
1 → 1 → odd
2 → 0 → even
3 → 1 → odd
```

So:

```asm
TEST BL, 1
```

checks:

> Is BL odd?

---

# 7. `JNZ WANT_GREATER`

Immediately after:

```asm
TEST BL, 1
JNZ WANT_GREATER
```

If the result was non-zero:

```text
BL is odd
```

then:

```asm
JNZ WANT_GREATER
```

jumps to the code that requires:

```text
left > right
```

If BL is even, no jump occurs.

So:

```text
BL even → require <
BL odd  → require >
```

Perfect for zig-zag.

---

# 8. Even index case: require `<`

Suppose:

```text
BL = 0
```

Then we need:

```text
a[0] < a[1]
```

The code is:

```asm
CMP AL, AH
JB PAIR_OK
```

Let's understand `CMP`.

---

# 9. `CMP AL, AH`

```asm
CMP AL, AH
```

conceptually performs:

```text
AL - AH
```

but it throws away the result.

It only updates the flags.

You already know this kind of idea from 8085 `CMP`.

In 8085:

```asm
CMP B
```

compares accumulator A against B.

Here:

```asm
CMP AL, AH
```

compares AL against AH.

---

# 10. `JB` means unsigned "below"

```asm
JB PAIR_OK
```

means:

```text
Jump if Below
```

For unsigned numbers:

```text
AL < AH
```

Since your values are bytes from:

```text
0 to 255
```

they are **unsigned**.

So `JB` is the correct conditional jump.

Example:

```text
AL = 20
AH = 50
```

then:

```text
20 < 50
```

so:

```asm
JB PAIR_OK
```

jumps.

No swap is needed.

---

# 11. What if AL is not below AH?

Suppose:

```text
AL = 80
AH = 20
```

For an even pair, we require:

```text
80 < 20
```

which is false.

So:

```asm
JB PAIR_OK
```

does not jump.

Then:

```asm
JMP SHORT SWAP_PAIR
```

forces a swap.

---

# 12. Odd index case: require `>`

Now suppose:

```text
BL = 1
```

We need:

```text
a[1] > a[2]
```

The code jumps here:

```asm
WANT_GREATER:
    CMP AL, AH
    JA PAIR_OK
```

`JA` means:

```text
Jump if Above
```

for unsigned values.

So:

```text
AL > AH
```

means the pair is already correct.

Example:

```text
AL = 90
AH = 30
```

Then:

```text
90 > 30
```

so:

```asm
JA PAIR_OK
```

jumps.

---

# 13. Otherwise swap

If the relation is wrong:

```asm
SWAP_PAIR:
    MOV [SI], AH
    MOV [SI+1], AL
```

This is elegant.

Remember:

```text
AL = original left
AH = original right
```

Before:

```text
[SI]   = AL
[SI+1] = AH
```

After:

```asm
MOV [SI], AH
MOV [SI+1], AL
```

we get:

```text
[SI]   = original right
[SI+1] = original left
```

So the values are swapped.

---

# 14. Example of the swap

Suppose the first pair is:

```text
8 3
```

We require:

```text
a[0] < a[1]
```

but:

```text
8 < 3
```

is false.

Initially:

```text
AL = 8
AH = 3
```

Then:

```asm
MOV [SI], AH
```

gives:

```text
a[0] = 3
```

and:

```asm
MOV [SI+1], AL
```

gives:

```text
a[1] = 8
```

Result:

```text
3 8
```

Now:

```text
3 < 8
```

correct.

---

# 15. Then advance only one position

This is important:

```asm
INC SI
```

not:

```asm
ADD SI, 2
```

Why?

Because the pairs overlap.

We compare:

```text
a[0], a[1]
```

then:

```text
a[1], a[2]
```

then:

```text
a[2], a[3]
```

So only move one element each time.

---

# 16. Why this algorithm works

Let's run an example.

Suppose input:

```text
8 3 7 2
```

We need:

```text
a0 < a1 > a2 < a3
```

### Pair 0

Current:

```text
8 3
```

Need:

```text
8 < 3
```

false.

Swap:

```text
3 8 7 2
```

Now:

```text
3 < 8
```

good.

---

### Pair 1

Now compare:

```text
8 7
```

Need:

```text
8 > 7
```

true.

No swap:

```text
3 8 7 2
```

---

### Pair 2

Compare:

```text
7 2
```

Need:

```text
7 < 2
```

false.

Swap:

```text
3 8 2 7
```

Now:

```text
3 < 8 > 2 < 7
```

Done.

That is the core idea.

---

# 17. One subtle issue: equality

The question requires strict relations:

```text
<
>
<
>
```

But consider equal values:

```text
5 5
```

For `<`, equality is wrong.

The code does:

```asm
CMP AL, AH
JB PAIR_OK
```

Since `5 < 5` is false, it swaps.

But swapping equal values gives:

```text
5 5
```

which is still not `<`.

Same problem for `>`.

So this algorithm cannot guarantee **strict** zig-zag if duplicate values exist.

For example:

```text
10 10
```

can never satisfy:

```text
10 < 10
```

or:

```text
10 > 10
```

That is a property of the problem itself, not really a bug in swapping.

If duplicates are permitted, strict zig-zag may be mathematically impossible.

---

# 18. Why use `JB` and `JA` rather than `JL` and `JG`?

This is an important x86 concept.

There are different comparisons for:

```text
unsigned numbers
signed numbers
```

Your byte inputs are:

```text
0–255
```

So they're unsigned.

Therefore use:

```text
JB = below
JA = above
```

For signed numbers, you'd use:

```text
JL = less
JG = greater
```

Example byte:

```text
FFH
```

Unsigned interpretation:

```text
255
```

Signed interpretation:

```text
-1
```

So the choice matters.

Here:

```text
0–255 → JB/JA
```

is correct.

---

# 19. `SHORT` in `JMP SHORT SWAP_PAIR`

You've seen:

```asm
JMP SHORT SWAP_PAIR
```

`SHORT` tells MASM the destination is nearby.

A short jump uses a small displacement.

For learning purposes, read it simply as:

```asm
JMP SWAP_PAIR
```

The program explicitly says `SHORT` because the target label is close.

You do not need to focus on jump encoding yet.

# 20. Input section

Now let's look briefly at the setup before the algorithm.

```asm
MOV DI, 4000H
MOV CX, 20
```

Means:

```text
DI = where input should be stored
CX = 20 numbers
```

Then:

```asm
MOV [DI], AL
INC DI
```

stores each number in:

```text
4000H
4001H
4002H
...
4013H
```

Why `4013H`?

Because 20 decimal = `14H`.

Offsets:

```text
4000H through 4013H
```

contain 20 bytes.

# 21. Invalid input handling is different from Q1

Question 1 stopped completely on invalid input.

Here:

```asm
BAD_INPUT:
    CALL PRINT_NEWLINE
    LEA DX, BAD_TEXT
    CALL PRINT_STRING
    JMP INPUT_LOOP
```

it simply prints an error and asks again.

That's better UX.

And because `PRINT_STRING` preserves CX, the loop count isn't destroyed.

---

# 22. Why preservation matters here

Look at:

```asm
PRINT_STRING PROC NEAR
    PUSH AX
    PUSH CX
    PUSH DX
```

Why preserve CX?

Because the caller may currently be doing:

```asm
MOV CX, 20
...
LOOP INPUT_LOOP
```

If `PRINT_STRING` changed CX without restoring it, the outer loop would break.

So this procedure saves:

```text
AX
CX
DX
```

and restores them before returning.

This is a good procedure-design habit.

---

# 23. `READ_BYTE` differs from Question 1

The decimal conversion here is simpler:

```asm
MOV AX, BX
MOV DX, 10
MUL DX
ADD AX, DI
```

Here `MUL DX` is a **16-bit multiplication**.

Important x86 rule:

For:

```asm
MUL DX
```

with a 16-bit operand, the CPU computes:

```text
AX × DX → DX:AX
```

That means the result is potentially 32-bit.

Since BX never grows past 255 during valid input, this is safe.

Conceptually the code calculates:

```text
old value × 10 + digit
```

just like Q1.

---

# 24. Why store digit in DI?

This section:

```asm
MOV DL, [SI]
...
SUB DL, '0'
XOR DH, DH
MOV DI, DX
```

converts the ASCII digit into a number and stores it in DI.

Why not leave it in DX?

Because immediately afterward:

```asm
MOV DX, 10
MUL DX
```

DX is needed as the multiplier.

So DI temporarily keeps the digit safe.

Example:

```text
typed digit = 7

DX = 0007H
DI = 0007H
```

then:

```text
DX = 10
```

can safely overwrite DX.

---

# 25. PRINT_ARRAY

This procedure is straightforward:

```asm
PRINT_ARRAY PROC NEAR
```

It assumes:

```text
SI = address of first byte
```

Then:

```asm
MOV CX, 20
```

sets 20 elements.

Inside:

```asm
MOV AL, [SI]
CALL PRINT_BYTE
```

prints the current byte.

Then:

```asm
MOV DL, ' '
MOV AH, 02H
INT 21H
```

prints a space.

Then:

```asm

LOOP PRINT_ARRAY_NEXT
```

moves through all 20 bytes.

# 26. One very important new idea: overlapping local corrections

This question teaches a useful algorithmic principle.

The program does **not sort the whole array**.

Instead, it only corrects each neighboring pair according to its required relation.

So:

```text
pair 0 → enforce <
pair 1 → enforce >
pair 2 → enforce <
...
```

This is much cheaper and simpler than sorting.

For this requirement, full sorting would be unnecessary.

---

# 27. Equivalent high-level pseudocode

The MASM core:

```asm
MOV SI, 4000H
MOV CX, 19
XOR BL, BL
```

followed by the loop is equivalent to:

```text
for i = 0 to 18:

    left  = a[i]
    right = a[i+1]

    if i is even:
        if left >= right:
            swap(left, right)

    else:
        if left <= right:
            swap(left, right)
```

That is exactly what the assembly is implementing.

---

# 28. C-style equivalent

Since this may help you visualize it:

```c
for (int i = 0; i < 19; i++) {
    if (i % 2 == 0) {
        if (a[i] >= a[i + 1]) {
            swap(a[i], a[i + 1]);
        }
    } else {
        if (a[i] <= a[i + 1]) {
            swap(a[i], a[i + 1]);
        }
    }
}
```

Then map that to assembly:

```text
i                 → BL
a[i] address      → SI
a[i]              → AL
a[i+1]            → AH
i % 2             → TEST BL,1
comparison        → CMP
if                 → conditional jump
swap               → MOV [SI],AH / MOV [SI+1],AL
loop counter       → CX
```

That's a very useful way to learn assembly.

# 29. 8085 comparison

Suppose in 8085 you wanted adjacent bytes.

You might do something conceptually like:

```asm
LXI H, 4000H
MOV A, M
INX H
MOV B, M
```

In x86:

```asm
MOV SI, 4000H
MOV AL, [SI]
MOV AH, [SI+1]
```

x86 lets you access both locations without temporarily changing SI.

That's one place where x86 addressing is much more flexible.

# 31. What the flags are doing

You don't see the flags directly, but many instructions depend on them.

For example:

```asm
CMP AL, AH
```

changes flags.

Then:

```asm
JB
```

or:

```asm
JA
```

checks those flags.

Similarly:

```asm
TEST BL, 1
```

changes the Zero Flag.

Then:

```asm
JNZ WANT_GREATER
```

checks that Zero Flag.

So a common assembly pattern is:

```text
instruction that sets flags
↓
conditional jump that reads flags
```

Examples:

```asm
CMP AL, AH
JB SOMEWHERE
```

and:

```asm
TEST BL, 1
JNZ SOMEWHERE
```

This is central to assembly programming.

# 32. One thing you should be able to explain orally

If your teacher asks:

> Why is `BL` used?

You can say:

> BL stores the current adjacent-pair index. Its least significant bit is tested using `TEST BL,1`. An even index requires `a[i] < a[i+1]`, whereas an odd index requires `a[i] > a[i+1]`.

If asked:

> Why is CX initialized to 19?

Say:

> Twenty elements contain nineteen adjacent pairs, so nineteen comparisons are required.

If asked:

> Why `JB` and `JA`?

Say:

> The array contains unsigned byte values from 0 to 255, so unsigned comparison jumps are used.
