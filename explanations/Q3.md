```asm
; Question 3
; Read one hexadecimal byte (00H-FFH) as two typed hex digits and print
; the value in hex plus, if printable, the ASCII character it represents.

STACKSEG SEGMENT PARA STACK 'STACK'
    DW 128 DUP (?)
STACKSEG ENDS

DATASEG SEGMENT PARA PUBLIC 'DATA'
    Q3_TITLE      DB 13,10,'QUESTION 3 - HEX BYTE TO ASCII CHARACTER',13,10,'$'
    PROMPT_TEXT   DB 'Enter a hex byte (00-FF): $'
    BAD_TEXT      DB 'Invalid input. Enter exactly two hex digits (0-9, A-F, a-f).',13,10,'$'
    HEX_LABEL     DB 'Hex value: $'
    ASCII_LABEL   DB 'ASCII value: $'
    NOT_PRINTABLE_TEXT DB 'not printable$'

    ; DOS function 0AH buffer: maximum length, actual length, characters.
    ; Valid input is exactly 2 typed characters. Following the same
    ; empirically-verified rule established for Q2 in this authentic
    ; DOSBox 0.74-3 / MASM 5.10 environment (typing exactly maxlen
    ; characters never returns from INT 21H/AH=0AH here), maxlen must be
    ; set higher than any erroneous entry length a user could plausibly
    ; type. maxlen=4 was tried first but confirmed to hang on a 4-character
    ; bad entry (e.g. "12AB") because 4 characters lands exactly on
    ; maxlen=4; maxlen=5 leaves headroom so a 3-4 character erroneous
    ; entry is cleanly rejected instead. The char area is sized maxlen+1
    ; to also hold the CR DOS writes after the typed characters.
    INPUT_BUFFER  DB 5,0,6 DUP (0)
DATASEG ENDS

CODESEG SEGMENT PARA PUBLIC 'CODE'
    ASSUME CS:CODESEG, DS:DATASEG, SS:STACKSEG

START:
    MOV AX, DATASEG
    MOV DS, AX

    LEA DX, Q3_TITLE
    CALL PRINT_STRING

INPUT_LOOP:
    LEA DX, PROMPT_TEXT
    CALL PRINT_STRING

    LEA DX, INPUT_BUFFER
    MOV AH, 0AH
    INT 21H

    CMP INPUT_BUFFER+1, 2
    JNE BAD_INPUT

    MOV AL, INPUT_BUFFER+2
    CALL HEX_NIBBLE
    JC BAD_INPUT
    MOV BL, AL
    SHL BL, 1
    SHL BL, 1
    SHL BL, 1
    SHL BL, 1

    MOV AL, INPUT_BUFFER+3
    CALL HEX_NIBBLE
    JC BAD_INPUT
    OR BL, AL

    CALL PRINT_NEWLINE

    LEA DX, HEX_LABEL
    CALL PRINT_STRING
    MOV DL, INPUT_BUFFER+2
    MOV AH, 02H
    INT 21H
    MOV DL, INPUT_BUFFER+3
    MOV AH, 02H
    INT 21H
    MOV DL, 'H'
    MOV AH, 02H
    INT 21H
    CALL PRINT_NEWLINE

    CMP BL, 20H
    JB NOT_PRINTABLE
    CMP BL, 7EH
    JA NOT_PRINTABLE

    LEA DX, ASCII_LABEL
    CALL PRINT_STRING
    MOV DL, BL
    MOV AH, 02H
    INT 21H
    CALL PRINT_NEWLINE
    JMP DONE

NOT_PRINTABLE:
    LEA DX, ASCII_LABEL
    CALL PRINT_STRING
    LEA DX, NOT_PRINTABLE_TEXT
    CALL PRINT_STRING
    CALL PRINT_NEWLINE
    JMP DONE

BAD_INPUT:
    CALL PRINT_NEWLINE
    LEA DX, BAD_TEXT
    CALL PRINT_STRING
    JMP INPUT_LOOP

DONE:
    MOV AX, 4C00H
    INT 21H

; Print the dollar-terminated string at DS:DX.
PRINT_STRING PROC NEAR
    PUSH AX
    PUSH DX
    MOV AH, 09H
    INT 21H
    POP DX
    POP AX
    RET
PRINT_STRING ENDP

; Print a carriage return and line feed.
PRINT_NEWLINE PROC NEAR
    PUSH AX
    PUSH DX
    MOV DL, 13
    MOV AH, 02H
    INT 21H
    MOV DL, 10
    MOV AH, 02H
    INT 21H
    POP DX
    POP AX
    RET
PRINT_NEWLINE ENDP

; Convert one ASCII hex digit in AL to its value (0-15) in AL.
; Accepts '0'-'9', 'A'-'F', and 'a'-'f'. Sets carry for any other input.
HEX_NIBBLE PROC NEAR
    CMP AL, '0'
    JB HN_BAD
    CMP AL, '9'
    JA HN_CHECK_UPPER
    SUB AL, '0'
    CLC
    RET
HN_CHECK_UPPER:
    CMP AL, 'A'
    JB HN_BAD
    CMP AL, 'F'
    JA HN_CHECK_LOWER
    SUB AL, 'A' - 10      ; Convert 'A'-'F' to 10-15
    CLC
    RET
HN_CHECK_LOWER:
    CMP AL, 'a'
    JB HN_BAD
    CMP AL, 'f'
    JA HN_BAD
    SUB AL, 'a' - 10
    CLC
    RET
HN_BAD:
    STC
    RET
HEX_NIBBLE ENDP

CODESEG ENDS
END START
```

Question 3 is a nice step up because now you’re learning **hexadecimal input**, **nibbles**, **bit shifting**, and the connection between a byte value and its ASCII character. 🔥

The actual goal is:

> Read exactly two hex digits like `41`, convert them into one byte `41H`, then print the hex value and, if that byte is a printable ASCII code, print the corresponding character.

For example:

```text
Input: 41

Hex value: 41H
ASCII value: A
```

because ASCII `41H` is `'A'`.

---

# 1. First new idea: what is a nibble?

A byte is 8 bits:

```text
8 bits = 1 byte
```

A **nibble** is 4 bits.

So one byte contains two nibbles:

```text
        8-bit byte
┌────────────┬────────────┐
│ high nibble│ low nibble │
│   4 bits   │   4 bits   │
└────────────┴────────────┘
```

For example:

```text
4AH
```

has:

```text
high nibble = 4
low nibble  = A
```

Binary:

```text
4 = 0100
A = 1010

4AH = 0100 1010
```

This is why exactly **two hex digits represent one byte**.

---

# 2. Input is text, not a number yet

Suppose you type:

```text
4A
```

DOS gives you two ASCII characters:

```text
'4'
'A'
```

These are not initially the numeric nibble values:

```text
4
10
```

So the program must convert each ASCII hex digit.

That's what this procedure does:

```asm
HEX_NIBBLE PROC NEAR
```

# 3. Main input section


prints:

Then:

# 4. Require exactly two characters

```asm

JNE BAD_INPUT
```

Remember:

```text
INPUT_BUFFER+1
```

contains the number of characters typed.

So if you type:

```text
4A
```

the length is:

```text
2
```

and the program continues.

But:

```text
A
123
XYZ
```

all fail because their lengths are not exactly two.

`JNE` means:

```text
Jump if Not Equal
```

So:

```asm

JNE BAD_INPUT
```

means:

> If the number of typed characters is not 2, reject the input.

# 5. First hex digit

Now:

```asm
MOV AL, INPUT_BUFFER+2
CALL HEX_NIBBLE
```

`INPUT_BUFFER+2` contains the first character.

Suppose you typed:

```text
4A
```

then:

```text
INPUT_BUFFER+2 = '4'
INPUT_BUFFER+3 = 'A'
```

So:

```asm
MOV AL, INPUT_BUFFER+2
```

gives:

```text
AL = ASCII '4'
```

Then:

```asm
CALL HEX_NIBBLE
```

converts it into:

```text
AL = 4
```

---

# 6. Check whether conversion succeeded

```asm
JC BAD_INPUT
```

`JC` means:

```text
Jump if Carry
```

The procedure uses carry as an error signal:

```text
CF = 0 → valid hex digit
CF = 1 → invalid hex digit
```

So if you type:

```text
G
@
Z
```

`HEX_NIBBLE` sets the Carry Flag and the program rejects the input.

This is the same style you saw in previous questions.

---

# 7. Store the first nibble

```asm
MOV BL, AL
```

After conversion:

```text
AL = first nibble
```

So now:

```text
BL = first nibble
```

For input:

```text
4A
```

we have:

```text
BL = 04H
```

But we want this `4` to become the **high nibble** of the final byte.

The final byte should be:

```text
4AH
```

not:

```text
04H
```

So we must shift it left four bits.

---

# 8. Why shift four times?

```asm
SHL BL, 1
SHL BL, 1
SHL BL, 1
SHL BL, 1
```

Each `SHL` shifts bits left by one position.

Start:

```text
BL = 0000 0100
```

After one shift:

```text
0000 1000
```

After two:

```text
0001 0000
```

After three:

```text
0010 0000
```

After four:

```text
0100 0000
```

That is:

```text
40H
```

So:

```text
4 → 40H
```

In general:

```text
nibble << 4 = nibble × 16
```

because each hex position represents a power of 16.

So for input:

```text
4A
```

after shifting:

```text
BL = 40H
```

---

# 9. Second digit

Now:

```asm
MOV AL, INPUT_BUFFER+3
CALL HEX_NIBBLE
JC BAD_INPUT
```

For input:

```text
4A
```

we load:

```text
AL = 'A'
```

and `HEX_NIBBLE` converts that to:

```text
AL = 10 = 0AH
```

So now:

```text
BL = 40H
AL = 0AH
```

---

# 10. Combine the two nibbles

Now:

```asm
OR BL, AL
```

This is the clever part.

We currently have:

```text
BL = 0100 0000
AL = 0000 1010
```

Bitwise OR:

```text
0100 0000
OR
0000 1010
-----------
0100 1010
```

which is:

```text
4AH
```

So:

```asm
OR BL, AL
```

combines the high nibble and low nibble.

The general formula is:

```text
byte = (first_digit << 4) OR second_digit
```

For example:

```text
'7' → 7
'F' → 15

7 << 4 = 70H
70H OR 0FH = 7FH
```

This is a very important assembly technique.

---

# 11. Why OR and not ADD?

You could mathematically do:

```text
40H + 0AH = 4AH
```

But `OR` is conceptually better here because the two bit fields don't overlap:

```text
high nibble = xxxx0000
low nibble  = 0000yyyy
```

So OR simply merges them:

```text
xxxxyyyy
```

It expresses the intent very clearly.

---

# 12. Printing the hex value

After conversion:

```asm
CALL PRINT_NEWLINE
```

Then:

```asm
LEA DX, HEX_LABEL
CALL PRINT_STRING
```

prints:

```text
Hex value:
```

Now look at this:

```asm
MOV DL, INPUT_BUFFER+2
MOV AH, 02H
INT 21H
```

It prints the **original first typed character**.

Then:

```asm
MOV DL, INPUT_BUFFER+3
MOV AH, 02H
INT 21H
```

prints the second one.

Finally:

```asm
MOV DL, 'H'
MOV AH, 02H
INT 21H
```

prints:

```text
H
```

So if you typed:

```text
4A
```

the output becomes:

```text
Hex value: 4AH
```

Notice the program doesn't reconvert BL back into printable hex digits. It simply reuses the two characters the user originally typed.

---

# 13. Small consequence of that design

If the user enters:

```text
af
```

the numeric byte becomes:

```text
AFH
```

but the printed result is:

```text
afH
```

because it prints the original characters.

That is not mathematically wrong, because hex digits are case-insensitive.

It just means the display isn't normalized to uppercase.

---

# 14. Now the ASCII part

At this point:

```text
BL = actual byte value
```

For example:

```text
BL = 41H
```

Now the program checks:

```asm
CMP BL, 20H
JB NOT_PRINTABLE
CMP BL, 7EH
JA NOT_PRINTABLE
```

Why `20H` and `7EH`?

Because standard printable ASCII characters are in the range:

```text
20H through 7EH
```

That includes:

```text
20H = space
21H = !
...
30H = 0
...
41H = A
...
61H = a
...
7EH = ~
```

Values below `20H` are mainly control characters such as:

```text
00H = NUL
09H = TAB
0AH = LF
0DH = CR
```

And:

```text
7FH
```

is DEL, also not printable.

---

# 15. `JB NOT_PRINTABLE`

```asm
CMP BL, 20H
JB NOT_PRINTABLE
```

means:

> If BL is below `20H`, it is not printable.

Since bytes are unsigned, `JB` is appropriate.

---

# 16. `JA NOT_PRINTABLE`

```asm
CMP BL, 7EH
JA NOT_PRINTABLE
```

means:

> If BL is above `7EH`, it is not printable.

So only this range survives:

```text
20H ≤ BL ≤ 7EH
```

# 17. Printing the ASCII character

If printable:

```asm
LEA DX, ASCII_LABEL
CALL PRINT_STRING
```

prints:

```text
ASCII value:
```

Then:

```asm
MOV DL, BL
MOV AH, 02H
INT 21H
```

prints the byte in BL as a character.

Suppose:

```text
BL = 41H
```

Then:

```text
DL = 41H
```

DOS interprets `41H` as the ASCII code:

```text
'A'
```

So the screen shows:

```text
ASCII value: A
```

This is the fundamental connection:

```text
number 41H
     ↓ interpreted as ASCII
character 'A'
```

```text
30
```

First nibble:

```text
'3' → 3
3 << 4 → 30H
```

Second nibble:

```text
'0' → 0
```

Combine:

```text
30H OR 00H = 30H
```

ASCII:


So output:

```text
ASCII value: 0
```

Notice the distinction:

```text
typed "30" → hexadecimal number 30H → ASCII character '0'
```

```text
7 << 4 = 70H
```

```text
ASCII value: z
```

# 20. Example with `0A`

Input:

```text
0A
```

Conversion gives:

```text
0AH
```

But:

```text
0AH < 20H
```

so it is treated as non-printable.


# 21. Now understand `HEX_NIBBLE`

This is the most important helper procedure in Question 3.

```asm
HEX_NIBBLE PROC NEAR
```

Input:

```text
AL = ASCII character
```

Output:

```text
AL = value 0–15
CF = 0 if valid
CF = 1 if invalid
```

It must handle three ranges:

```text
'0'–'9'
'A'–'F'
'a'–'f'
```

---

# 22. Decimal digit case

First:

```asm
CMP AL, '0'
JB HN_BAD
```

If the character is below `'0'`, it cannot be a hex digit.

Then:

```asm
CMP AL, '9'
JA HN_CHECK_UPPER
```

If it is no greater than `'9'`, then we know:

```text
'0' ≤ AL ≤ '9'
```

So:

```asm
SUB AL, '0'
```

converts ASCII to the numeric value.

Example:

```text
AL = '7' = 37H

37H - 30H = 07H
```

Then:

```asm
CLC
RET
```

returns success.

---

# 23. Uppercase A-F

If the character was above `'9'`, execution reaches:

```asm
HN_CHECK_UPPER:
    CMP AL, 'A'
    JB HN_BAD
```

If it is below `'A'`, it is invalid.

That rejects characters between `'9'` and `'A'`, such as:

```text
:
;
<
=
>
?
@
```

Then:

```asm
CMP AL, 'F'
JA HN_CHECK_LOWER
```

So if:

```text
'A' ≤ AL ≤ 'F'
```

it is a valid uppercase hex digit.

---

# 24. The unusual line

Now:

```asm
SUB AL, 'A' - 10
```

This deserves careful explanation.

MASM calculates:

```text
'A' - 10
```

at assembly time.

ASCII `'A'` is:

```text
41H = 65 decimal
```

Therefore:

```text
65 - 10 = 55
```

So the instruction is effectively:

```asm
SUB AL, 55
```

Why?

Because we want:

```text
'A' → 10
'B' → 11
'C' → 12
...
'F' → 15
```

For `'A'`:

```text
65 - 55 = 10
```

For `'F'`:

```text
70 - 55 = 15
```

So it works perfectly.

---

# 25. Easier way to think about it

This:

```asm
SUB AL, 'A' - 10
```

means conceptually:

```text
value = character - 'A' + 10
```

Example:

```text
'C'

'C' - 'A' = 2
2 + 10 = 12
```

And:

```text
12 = CH
```

as a hexadecimal nibble.

---

# 26. Lowercase a-f

The lowercase block is the same idea:

```asm
HN_CHECK_LOWER:
    CMP AL, 'a'
    JB HN_BAD
    CMP AL, 'f'
    JA HN_BAD
    SUB AL, 'a' - 10
```

So:

```text
'a' → 10
'b' → 11
...
'f' → 15
```

This lets the user enter either:

```text
AF
```

or:

```text
af
```

or even:

```text
aF
```

All are accepted.

---

# 27. Invalid characters

Anything else reaches:

```asm
HN_BAD:
    STC
    RET
```

So:

```text
CF = 1
```

For example:

```text
'G'
'x'
'@'
'/'
```

are rejected.

# 28. Flow of `HEX_NIBBLE`

You can visualize the procedure like this:

```text
                    character in AL
                         |
                  is it '0'–'9'?
                    /          \
                  yes          no
                   |            |
              AL -= '0'    is it 'A'–'F'?
                                /       \
                              yes       no
                               |         |
                     AL = value 10–15    |
                                         |
                                  is it 'a'–'f'?
                                      /      \
                                    yes      no
                                     |        |
                             AL = 10–15    invalid
```

That's the whole procedure.

---

# 29. Why the Carry Flag is useful

Instead of returning a separate boolean variable like:

```text
valid = true
```

assembly often uses processor flags.

So the procedure contract is:

```text
AL = converted value
CF = status
```

Then the caller can simply do:

```asm
CALL HEX_NIBBLE
JC BAD_INPUT
```

Very compact.

This is similar to using flags in 8085 subroutines.

---

# 30. `OR BL, AL` versus logical OR in C

One thing to be careful about:

Assembly:

```asm
OR BL, AL
```

is **bitwise OR**.

Equivalent C operation:

```c
bl = bl | al;
```

not:

```c
bl = bl || al;
```

For:

```text
BL = 40H
AL = 0AH
```

we want bit merging:

```text
40H | 0AH = 4AH
```

---

# 31. High-level equivalent

The heart of the conversion could be written conceptually as:

```c
high = hex_to_value(first);
low  = hex_to_value(second);

value = (high << 4) | low;
```

Then:

```c
if (value >= 0x20 && value <= 0x7E)
    print((char)value);
else
    print("not printable");
```

And that's almost exactly what the MASM program does.

---

# 32. Mapping that C-like logic to MASM

```text
high = hex_to_value(first)
↓
MOV AL, INPUT_BUFFER+2
CALL HEX_NIBBLE
```

```text
high << 4
↓
MOV BL, AL
SHL BL, 1 × 4
```

```text
low = hex_to_value(second)
↓
MOV AL, INPUT_BUFFER+3
CALL HEX_NIBBLE
```

```text
value = high | low
↓
OR BL, AL
```

This is a very clean example of translating high-level logic to assembly.

# 33. Connection to 8085

You already know instructions like:

```asm
ANI
ORI
CMP
JC
JNC
```

So several concepts here should feel familiar.

The main new thing is that x86 gives you flexible instructions such as:

```asm
SHL BL, 1
```

and lets you use many registers directly.

In 8085, shifting typically requires rotate instructions such as:

```asm
RLC
```

and careful carry handling.

In x86:

```asm
SHL BL, 1
```

directly performs a logical left shift.

---

# 34. Important distinction: hex value vs ASCII code

This question exists largely to teach this distinction.

Suppose you type:

```text
41
```

There are three different ideas involved:

```text
characters typed:     '4' '1'
                         ↓ conversion
numeric byte:          41H
                         ↓ ASCII interpretation
character:             'A'
```

This is crucial.

The text:

```text
"41"
```

is not initially the byte `41H`.

It's two ASCII characters:

```text
'4' = 34H
'1' = 31H
```

The program converts those two ASCII digits into the actual byte:

```text
41H
```

Then interprets that byte using the ASCII table.

---

# 35. Why `BL` is a good choice

After conversion, BL stores the final byte:

```text
BL = 00H–FFH
```

AL is repeatedly used by `HEX_NIBBLE`, so keeping the assembled byte in BL avoids conflicts.

This is another general assembly principle:

> Give registers temporary roles based on what the algorithm needs.

There is no rule saying BL must always contain a particular type of data.

# 36. PRINT_STRING and PRINT_NEWLINE

These are almost identical to what you already saw.

```asm
PRINT_STRING PROC NEAR
    PUSH AX
    PUSH DX
    MOV AH, 09H
    INT 21H
    POP DX
    POP AX
    RET
PRINT_STRING ENDP
```

It preserves AX and DX because it temporarily modifies AH.

And:

```asm
PRINT_NEWLINE PROC NEAR
```

prints ASCII:

```text
13 = carriage return
10 = line feed
```

using DOS function `02H`.

Nothing fundamentally new here.

# 37. New instructions/concepts in Question 3

The major new things are:

| Concept | Meaning |
|---|---|
| nibble | 4 bits |
| `SHL` | shift bits left |
| `OR` | combine bit fields |
| `JNE` | jump if not equal |
| hex conversion | `'A' → 10`, `'F' → 15` |
| ASCII printable range | `20H–7EH` |
| byte assembly | `(high << 4) \| low` |

Those are what I would prioritize studying.

# 38. Core algorithm you should understand

The most important section is:

```asm
MOV AL, INPUT_BUFFER+2
CALL HEX_NIBBLE
JC BAD_INPUT
MOV BL, AL

SHL BL, 1
SHL BL, 1
SHL BL, 1
SHL BL, 1

MOV AL, INPUT_BUFFER+3
CALL HEX_NIBBLE
JC BAD_INPUT

OR BL, AL
```

Read it in English:

> Convert the first hex character into a nibble, shift it left four positions so that it becomes the high nibble, convert the second character into the low nibble, and combine the two using bitwise OR to form the complete byte.

That sentence is worth remembering.

Let's trace everything.

Input:

```text
5C
```

First character:

```text
'5' → numeric 5
```

BL:

```text
0000 0101
```

Shift four:

```text

```

Second character:

```text
'C' → 12 = 0CH
```

AL:

```text
0000 1100
```

OR:

```text
0101 0000
0000 1100
-----------
0101 1100
```

Result:

```text
5CH
```

```text

```

Therefore:

```text

ASCII value: \
```

# 40. Another worked example: `FF`

Input:

```text
FF
```

First nibble:

```text
F → 15
15 << 4 = F0H
```

Second:

```text
F → 0FH
```

Combine:

```text
F0H OR 0FH = FFH
```

Check printable range:

```text
FFH > 7EH
```

so:

```text
ASCII value: not printable
```

# 41. What you should now know after Questions 1–3

Your progression is becoming quite clear:

```text
Question 1
→ arrays, pointers, loops, arithmetic

Question 2
→ comparisons, flags, conditional jumps, swapping

Question 3
→ nibbles, hexadecimal conversion, shifts, bitwise operations, ASCII
```

Question 3 introduces one of the most important low-level ideas you'll use later:

```text
bits can represent different things depending on how you interpret them
```

For example:

```text
41H
```

can simply be the number:

```text
65 decimal
```

or, when interpreted using ASCII:

```text
'A'
```

The bits are the same. **The interpretation changes.**

That's a fundamental assembly/computer-architecture concept. 🔥
